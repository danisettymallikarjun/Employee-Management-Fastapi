# Employee Records API

A FastAPI backend for managing employee records. This is stage 1 of the
project: records are stored **in memory** (a plain Python list) — there is
no database, authentication, frontend, or Docker setup yet. Data resets
whenever the application restarts.

## Tech Stack

- Python 3.12
- FastAPI
- Pydantic v2 (with `email-validator` for email validation)
- Uvicorn (ASGI server)
- Swagger UI (auto-generated by FastAPI at `/docs`)

## Setup & Execution

1. **Create and activate a virtual environment** (recommended):

   ```bash
   python -m venv venv
   source venv/bin/activate      # on Windows: venv\Scripts\activate
   ```

2. **Install dependencies:**

   ```bash
   pip install -r requirements.txt
   ```

3. **Run the application:**

   ```bash
   uv run uvicorn app.main:app --reload
   ```

4. **Open Swagger UI** in your browser to explore and test all endpoints:

   ```
   http://127.0.0.1:8000/docs
   ```

   ReDoc is also available at `http://127.0.0.1:8000/redoc`.

## API Endpoints

| Method | Path                | Description                |
|--------|---------------------|-----------------------------|
| GET    | `/health`           | Health check                |
| POST   | `/employees`        | Create an employee          |
| GET    | `/employees`        | List all employees          |
| GET    | `/employees/{id}`   | Get an employee by ID       |
| PUT    | `/employees/{id}`   | Update an employee (full replace) |
| DELETE | `/employees/{id}`   | Delete an employee          |

### Employee fields

| Field           | Type    | Notes                                    |
|-----------------|---------|-------------------------------------------|
| `id`            | int     | Auto-generated, starts at 1               |
| `name`          | string  | Required                                  |
| `email`         | string  | Required, must be a valid & unique email  |
| `department`    | string  | Required                                  |
| `primary_skill` | string  | Required                                  |
| `location`      | string  | Required                                  |
| `work_mode`     | string  | Required, must be `WFH` or `WFO`          |
| `is_active`     | bool    | Optional, defaults to `true`              |
| `created_at`    | datetime| Auto-generated (UTC)                      |

### Validation rules

- `name`, `email`, `department`, `primary_skill`, `location`, and `work_mode`
  are all required on create/update.
- `email` must be a syntactically valid email address and must be unique
  across all employees (returns `409 Conflict` on duplicates).
- `work_mode` only accepts `WFH` or `WFO` (returns `422` otherwise).
- Employee IDs in the URL path must be positive integers; `0` or negative
  values are rejected with `422` before any lookup happens.
- Requesting an employee ID that doesn't exist returns `404 Not Found`.
- All validation errors return a JSON body like `{"detail": "..."}` with an
  appropriate HTTP status code (`404`, `409`, or `422`).

### Sample request (create employee)

```json
POST /employees
{
  "name": "Sravan Kumar",
  "email": "sravan@example.com",
  "department": "Engineering",
  "primary_skill": "Python",
  "location": "Nellore",
  "work_mode": "WFH"
}
```

## Notes

### What I learned
- How FastAPI + Pydantic combine to get request validation, response
  serialization, and interactive Swagger docs almost for free, just by
  declaring types (e.g. `EmailStr`, an `Enum` for `work_mode`, `Path(gt=0)`
  for the ID).
- Structuring the app into `schemas.py` (data shape/validation) and
  `services.py` (business logic/storage) keeps `main.py` focused purely on
  HTTP routing, which will make it much easier to swap the in-memory list
  for a real database in a later stage without touching the API layer.
- FastAPI's default validation error format is quite verbose; overriding
  the `RequestValidationError` handler gives cleaner, more predictable
  error responses for API consumers.

### Difficulties faced
- Deciding how strict `PUT` should be: this implementation treats `PUT` as
  a full replace (all fields required), which is the standard REST
  convention, but it does mean a client can't send a partial update — that
  would need a separate `PATCH` endpoint in a later stage.
- Making sure ID validation (`gt=0`) happens at the path-parameter level
  (via `Path(..., gt=0)`) rather than deep inside the service layer, so
  invalid IDs are rejected early and consistently, before any lookup logic
  runs.
- Keeping the in-memory store thread-safe with a simple `Lock` even though
  Uvicorn's default single-worker async setup rarely triggers real race
  conditions — added for correctness rather than because it was strictly
  necessary at this scale.

### Assumptions made
- `PUT /employees/{id}` performs a **full replace** of all editable fields
  (not a partial patch); all fields required by `POST` are also required
  on `PUT`.
- Email uniqueness is checked case-insensitively (`Sravan@x.com` and
  `sravan@x.com` are treated as the same address).
- `created_at` is set once at creation time and is not modified by later
  updates.
- IDs are assigned sequentially starting at `1` and are never reused, even
  after a delete (e.g. deleting employee `1` does not make `1` available
  again).
- No database, authentication, frontend, or Docker setup was added, per the
  task scope — those are explicitly reserved for later stages.
